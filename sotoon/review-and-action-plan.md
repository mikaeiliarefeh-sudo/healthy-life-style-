# نقد نسخه‌ی بازنویسی + برنامه‌ی اکشن — مصرف آی‌پی پابلیک

> تحلیلِ نسخه‌ی بازنویسیِ داکیومنت (۷ آگوست ۲۰۲۶) در کنارِ داده‌های اکسل (اسنپ‌شات ۱ آگوست). مکملِ `ip-usage-analysis.md`.

## ۱. جمع‌بندی کلی
نسخه‌ی بازنویسی از نظر **مدل مفهومی درست و بالغ** شده: دو بُعدِ «وضعیت رزرو» (موقتی/رزرو) و «تارگتِ اتصال» (VM/VPC/LB/هیچ) را جدا کرده و هر فلوی ساخت و حذف را قدم‌به‌قدم بررسی کرده است. **سه ضعف** مانع از تبدیلِ آن به یک کیسِ قابل‌تصمیم برای لیدر است:
1. فرضِ «اتصال = مصرف» تست نشده.
2. عددهای کلیدی هنوز `؟`اند.
3. نه «اندازه‌ی جایزه» دارد نه برنامه‌ی اکشنِ اولویت‌بندی‌شده.

## ۲. نقاط قوت
- تفکیکِ درستِ «رزرو/موقتی» از «تارگتِ لینک».
- پیمایشِ کاملِ فلوهای ساخت (VM، VPC، LB از VM، LB از کوبر، کوبر) و حذف.
- تشخیصِ درستِ ریشه: پیچیدگیِ فلوی حذف (خصوصاً VPC و کوبرِ تودرتو)، نه صرفاً فراموشیِ کاربر.
- ثبتِ باگ‌های مشخص (LB نصفه، کلاستر گیرکرده در provisioning، پیام خطای اشتباه).
- هایلایتِ اینکه کاربر بابتِ آی‌پیِ رزروِ آزاد نوتیف نمی‌شود ولی هزینه می‌دهد.

## ۳. مشکلات و گپ‌ها
1. **فرضِ «اتصال = ترافیک = مصرف» تست نشده.** کلِ استدلالِ سلامتِ ۸۳۳ آی‌پیِ روی VM بر این فرض بنا است. اتصال ≠ ترافیک. → نیازمندِ داده‌ی ترافیکِ per-IP.
2. **VPC-بدون-VM مبهم مانده.** معیارِ تفکیک (درسِ ghabzino) اعمال نشده؛ از ۹۷ آی‌پیِ VPC-بدون-VM همه اسراف نیستند (بعضی egressِ مشروعِ کوبر/LB).
3. **عددهای کلیدی خالی (`؟`).** در بخش ۴ پر شده‌اند.
4. **«اندازه‌ی جایزه» غایب.** لیدر به عددِ آی‌پی/دلار نیاز دارد.
5. **برنامه‌ی اکشنِ اولویت‌بندی‌شده نیست.**
6. **متریکِ موفقیت و defaultهای هدف تعریف نشده.**
7. **سگمنت‌بندیِ مشتری غایب.** ~۱۰ مشتریِ برتر ۵۵٪ آی‌پیِ بی‌اتصال را نگه داشته‌اند (اسمارتک ۳۸ تا به‌تنهایی).

## ۴. عددهای پرشده (جایگزینِ `؟`ها)

| موضوع | مقدار |
|---|---|
| توزیع کل ۱۶۷۹ آی‌پی | VM/Link ۸۳۳ (۴۹.۶٪) · VPC-gw ۳۵۷ (۲۱.۳٪) · LB ۲۸۴ (۱۶.۹٪) · بی‌اتصال ۲۰۵ (۱۲.۲٪) |
| LBِ یتیمِ کوبر (IP مانده، LB نیست) | ۳۷ آی‌پی (۱۸٪ از بی‌اتصال‌ها) |
| VPC بدون هیچ سرور/VM | ۹۷ از ۳۵۷ گیت‌وی = ۲۷٪ (شیت تفصیلی: ۱۴۲ اینترفیس روی ۹۰ VPC) |
| تفکیک ۲۰۵ بی‌اتصال | ۱۵۱ رزروِ بلااستفاده · ۳۷ LBِ یتیمِ کوبر · ۱۷ تستی |
| رزرو/سنِ VPC-بدون-VM (۱۴۲تایی) | ۴۲ رزرو، ۱۰۰ غیررزرو · میانه‌ی سن ۱۴۲ روز · ۵۶ تا >۶ماه · ۱۹ تا >۱ سال |
| تمرکزِ مشتری | ~۱۰ مشتریِ برتر ≈ ۵۵٪ از ۲۰۵ بی‌اتصال |

## ۵. اندازه‌ی جایزه
- **قطعی (به‌هیچ‌چیز وصل نیست):** ۲۰۵ آی‌پی = ۱۲.۲٪.
  - سریع‌ترین/کم‌ریسک‌ترین: ۳۷ LBِ یتیم + ۱۷ تستی = **۵۴ آی‌پی** (بدونِ لمسِ مشتریِ فعال).
  - سپس: ۱۵۱ رزروِ بلااستفاده (اولویت با قدیمی‌ها).
- **مشروط (بعد از چکِ ترافیک):** تا ۹۷ آی‌پیِ VPC-بدون-VM.
- **سقفِ آدرس‌پذیر ≈ ۳۰۰ آی‌پی ≈ ۱۸٪ کل.**
- **ارزش:** ~۳۰۰ × ۳۵$ ≈ ~۱۰٬۵۰۰$ اینوِنتوریِ آزادشده + به‌تعویق‌انداختنِ خریدِ رنجِ بعدی (~۲۰۰۰ آی‌پی ≈ ۷۰هزار دلار خوابِ سرمایه).

## ۶. برنامه‌ی اکشن (فازبندی‌شده)

**فاز ۰ — داده (~۱ هفته):** کوئریِ ترافیکِ per-IP → بازطبقه‌بندیِ «متصل ولی بی‌ترافیک»؛ تفکیکِ ۹۷ به (الف: بی‌ترافیک / ب: کوبر)؛ تأییدِ بیل‌شدنِ یتیم‌ها با علی صفری.

**فاز ۱ — بردِ سریع (بازپس‌گیریِ موجودی):** نوتیف + آزادسازیِ ۵۴ یتیمِ سریع، سپس رزروهای قدیمی. هدف: بی‌اتصال از ۱۲.۲٪ به < ۵٪. شروع از ۱۰ مشتریِ برتر.

**فاز ۲ — رفعِ باگ (تا یتیمِ جدید تولید نشود):**
- cascade-deleteِ کلاستر کوبر (الان subnet + VPC + IP می‌ماند).
- LB نصفه‌کاره که IP می‌سازد و رها می‌کند.
- VPCِ ساخته‌شده از فلوی VM که با حذفِ VM پاک نمی‌شود.
- پیامِ خطای اشتباه هنگام تمام‌شدنِ آی‌پیِ رنج.

**فاز ۳ — اصلاحِ فلو/defaultها (تا کاربر بیش‌خرید نکند):**
- default = انتخاب از آی‌پیِ موجود، نه ساختِ جدید.
- default = موقتی، نه رزرو؛ انتقالِ تصمیمِ رزرو به زمانِ حذفِ منبع.
- صفحه‌ی حذفِ LB/VPC/کلاستر: نمایشِ منابعِ متصل + دکمه‌ی حذفِ درجا.
- نوتیفِ آی‌پیِ رزروِ بی‌مصرفِ بیل‌شده.

**فاز ۴ — بازدارنده (بعداً):**
- قیمتِ گران‌تر برای idle (الگوی AWS Elastic IP).
- TTL و حذفِ خودکار با هشدار.
- تشویقِ معماریِ NAT-gateway مشترک + LB به‌جای IP per-VM.

## ۷. متریکِ موفقیت
- نرخِ آی‌پیِ بی‌اتصال < ۵٪ (از ۱۲.۲٪).
- بازپس‌گیریِ ≥ ۲۰۵ آی‌پی در بازه‌ی هدف.
- صفر یتیمِ جدید از حذفِ کلاستر پس از رفعِ باگِ فاز ۲.

## ۸. جمع‌بندی برای مدیر (دو حالتِ نهاییِ هدررفت)

آی‌پیِ هدررفته دو حالتِ نهایی داره و هر کدوم ریشه‌ی فلویی متفاوتی دارن:

### حالتِ ۱ — آی‌پی به هیچی وصل نیست (Unattached): ۲۰۵ آی‌پی (۱۲.۲٪)
**استدلال:** ریسورس (وی ام یا لود بالانسر) حذف شده ولی چون آی‌پی رزرو بوده، آزاد نشده و به هیچی اشاره نمی‌کنه.

| فلو | باگ/مشکل | خروجی |
|---|---|---|
| حذفِ وی ام | آی‌پیِ رزرو پاک نمیشه و بابتِ هزینه‌اش یاداوری نمیشه | Unattached |
| حذفِ لود بالانسرِ دستی | آی‌پیش به انتخابِ کاربره (دیفالت رزرو نیست)؛ اگه کاربر رزرو زده باشه با حذفِ LB آزاد نمیشه و یاداوری نمیشه | Unattached (non-ske) |
| حذفِ کلاستر کوبر | LB سیستمی پاک میشه ولی آی‌پیِ رزروش می‌مونه | Unattached، پیشوندِ `ske-` = ۶۴ |
| باگِ LBِ نصفه | کاربر وسطِ ساخت drop می‌کنه، آی‌پی ساخته و رها میشه | Unattached |

مقصرِ مشترک: پیش‌فرض/انتخابِ **رزرو** + **نبودِ یاداوری هنگامِ حذف**. (۶۴ تای کوبر سیستمی و با `ske-` قابلِ‌شناساییه؛ ۱۴۱ تای non-ske رفتاریه.)

### حالتِ ۲ — آی‌پی وصله ولی ترافیک ازش رد نمیشه (Attached-idle): حداقل ۹۷ آی‌پی
**استدلال:** آی‌پیِ گیت‌ویِ VPC، egressِ مشترکِ VMهای داخلِ VPCه. اگر VPC هیچ VM نداشته باشه، ترافیکی از آی‌پی رد نمیشه — آی‌پی **وصله** (به گیت‌وی) ولی **بی‌مصرفه**. اینجا آی‌پی موقتیه نه رزرو؛ علتِ موندنش، پاک‌نشدنِ خودِ VPCه.

| فلو | باگ/مشکل | خروجی |
|---|---|---|
| حذفِ ناقصِ VPC | فلوی تو در تو (اول VM، بعد subnet، بعد VPC)؛ چند کلیک، بدونِ لینکِ مستقیم → کاربر VPC رو رها می‌کنه | VPCِ بدونِ VM با آی‌پیِ وصل |
| حذفِ کلاستر کوبر | ماشین‌ها و LB آبشاری پاک میشن ولی subnet + VPC + آی‌پیش نه | VPCِ بدونِ VM با آی‌پیِ وصل |

مقصرِ مشترک: **پیچیدگیِ فلوی حذفِ VPC** + **نبودِ حذفِ آبشاری** در حذفِ کلاستر.
> این ۹۷ کف است؛ آی‌پیِ LBِ بدونِ backend و آی‌پیِ روی VMِ بی‌ترافیک هم حالتِ ۲ ان ولی برای شمارششان به دیتای ترافیک نیاز داریم.

### چرا اصلاً آی‌پیِ مازاد وارد سیستم میشه (سمتِ ساخت)
پیش‌فرضِ «اتصال به اینترنت» + پیش‌فرضِ «ساختِ آی‌پیِ جدید» (به‌جای انتخاب از موجود) + امکانِ گرفتنِ آی‌پی هم‌زمان روی VPC و هم روی VM → کاربر بیشتر از نیازش می‌خره؛ بخشی بعداً به حالتِ ۱ و ۲ تبدیل میشن.

### چقدر حل میشه
- **حالتِ ۱ (۲۰۵):** ۶۴ کوبر (`ske-`) سیستمیه → رفعِ باگِ حذفِ آبشاری، بدونِ دخالتِ کاربر؛ ۱۴۱ non-ske رفتاریه → پیش‌فرضِ موقتی + یاداوری.
- **حالتِ ۲ (۹۷):** ساده‌سازیِ حذفِ VPC + حذفِ آبشاریِ کلاستر.
- **جمعاً تا ~۳۰۰ آی‌پی (~۱۸٪ از کل)** آزاد و خریدِ رنجِ بعدی به تعویق می‌افته.
